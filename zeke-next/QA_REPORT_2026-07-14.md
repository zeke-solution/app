# Zeke Baba QA and logic review

Date: 2026-07-14
Scope: code-level QA, production build, anonymous runtime smoke test, authorization/RLS review, and core deal-state workflow review.

## Outcome

The app compiles cleanly and its anonymous route protection works, but it is not ready for production workflow testing yet. One high-impact RLS mismatch affects names across the marketplace, and several multi-step money/content/dispute operations are not atomic and can leave deals stuck after a partial failure.

## Automated verification

- `npm run lint`: pass
- `npx tsc --noEmit --incremental false`: pass
- `npm run build`: pass; 31 routes generated
- Anonymous runtime smoke test: `/`, `/login`, `/register`, `/reset`, `/update-password`, `/about`, and `/privacy` returned 200
- Anonymous role guards: `/creator`, `/brand`, and `/admin` returned 307 to `/login`
- Anonymous agreement PDF request returned 401
- No automated unit, integration, database, or end-to-end test suite is configured in `package.json`

## Findings

### P1 - Cross-user names and locations are blocked by the profile RLS policy

The migration's `profiles_select` policy only permits a user to read their own row or an admin to read it. However, brand and creator pages repeatedly join `public.profiles` to show the other party's `display_name` and creator `location`. The separate `influencer_profiles` and `brand_profiles` policies allow cross-role reads, but that does not grant access to the joined `profiles` row.

Expected impact if migration 0002 is active:

- Brand discovery can show generic `Creator` names and blank locations.
- Creator offer, deal, chat, agreement, and profile screens can show generic `Brand` names.
- Brand deal and chat screens can show generic creator names.

Relevant code: `supabase/migrations/0002_security_hardening.sql:308`, `actions/creators.ts:22`, and the many `profiles!deals_*_fkey` joins in role pages.

Recommended fix: expose only safe public profile fields through a deliberately designed policy/view/RPC, then test both brand-to-creator and creator-to-brand reads with real authenticated accounts. Avoid broadly exposing all profile fields without deciding which fields are public.

### P1 - Core workflow mutations are split across non-transactional calls

Several business operations first insert/update a child record and then separately update the deal status:

- submission record -> `submitted`
- submission approval -> `approved`
- final link -> `link_submitted`
- payment record -> `payment_sent`
- payment confirmation -> `completed`
- dispute record -> `disputed`

If the second call fails, the first write remains. Unique indexes can then prevent a clean retry for final links, payments, and active disputes. This can produce a saved link/payment/dispute with a deal still in the prior status, leaving the UI unable to continue.

Relevant code: `actions/submissions.ts`, `actions/links.ts`, `actions/payments.ts`, and `actions/disputes.ts`; uniqueness constraints are in migration 0002 around lines 463-468.

Recommended fix: move each state transition into a security-definer PostgreSQL function that validates the actor and current state and performs all related writes in one transaction. The Shield and admin dispute-resolution functions already demonstrate this pattern.

### P2 - Some conditional updates treat zero affected rows as success

Multiple state-changing updates use `.eq("status", ...)` but only inspect `error`. Supabase can return no error when zero rows matched. Under a double click or concurrent action, the action may continue with timeline messages/notifications or report success even though it did not own the transition.

The submission review path has the clearest example: it conditionally updates a pending submission but does not request/verify the updated row before continuing. Similar checks exist in final-link and payment status updates.

Recommended fix: return the updated row with `.select(...).maybeSingle()` and require it to exist, or incorporate the work into the transactional RPCs recommended above.

### P2 - Live database migration and authenticated workflows remain unverified

This pass verified repository SQL, not the schema currently deployed in Supabase. The app depends on migration 0002 for state-machine triggers, RPCs, unique indexes, restricted privileges, and private submission storage. Without confirming the live migration state, the code-level security assumptions are not proven.

Recommended verification:

1. Confirm migrations 0001 and 0002 are applied in order.
2. Test with separate brand, creator, and admin accounts.
3. Attempt direct unauthorized PostgREST updates for role, Shield, deal state, submissions, and payments.
4. Exercise accept/decline, submission/revision, live link, payment, cancellation, dispute, and Shield flows.

### P3 - Terms of Service points to the Privacy page

The footer's `Terms of Service` link currently targets `/privacy`, so there is no distinct terms page. This is a product/legal-content gap rather than a runtime defect.

Relevant code: `components/marketing/Footer.tsx:61`.

### P3 - Regression safety is manual only

There is no `test` script or automated coverage for role boundaries and the deal state machine. These are the highest-risk parts of the product and are especially vulnerable to regressions as new states are added.

Recommended minimum suite:

- Database tests for every permitted and forbidden state transition
- Server-action tests for ownership and stale-state handling
- End-to-end happy paths for brand, creator, admin, cancellation, and dispute flows

## Priority order

1. Fix safe cross-user profile visibility.
2. Make the six core workflow transitions transactional.
3. Add affected-row checks/concurrency protection.
4. Confirm live migrations and run authenticated three-role QA.
5. Add a real Terms page and automated regression tests.
